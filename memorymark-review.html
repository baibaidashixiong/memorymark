审查发现

以下不是“最好都做”的愿望清单，而是按对结果可信度的影响排序。P0 应先处理，P1 决定工具是否有解释力，P2 是后续平台能力。

评分最低内存限制与延迟测试实际需求不一致

P0 · 必须修

参数层接受 192M，但延迟测试同时保留 128 MiB 数据区和 128 MiB 排列数组，实际至少需要 256 MiB。结果会在完成多个项目后才在 latency 项失败。依据：src/cli.c:143、src/memory.c:26、src/memory.c:28、src/bench_parallel.c:112。

建议把评分下限改为 256 MiB，并添加 255/256 MiB 边界测试。更长期可以设计低峰值环构建，但不应阻塞当前修复。

多线程总带宽实际上是“完成吞吐”，不是严格并行窗口带宽

P0 · 语义

总时间从主线程放行起算，但每个线程的字节数来自各自的开始/结束区间。线程启动偏斜、调度和过订阅都被计入分母，却仍被展示为 aggregate bandwidth 与 scaling efficiency。依据：src/bench_parallel.c:61、src/bench_parallel.c:146、src/bench_parallel.c:158。

建议输出每线程 start/end、最大起跑偏斜和活跃重叠率；要么改名为 completion throughput，要么按共同重叠窗口计算工作量。多线程分数应另列，不混入单线程 MMark。

128 MiB 固定工作集不能保证越过 LLC

P0 · 可比性

当前评分固定 128 MiB、warm/no-flush。128 MiB 以上的服务器 LLC 会让 MMark 主要反映 Cache 而非 DRAM，且不同机器含义不同。依据：src/score.c:20、README 的 Cache 限制说明。

建议把当前分数正式命名为 warm logical-access score，并输出与检测到的 LLC 的容量关系；新增独立的 DRAM-oriented profile，而不是静默改变所有机器的同一规格。

三轮 CV 不足以支撑 STABLE 标签

P0 · 统计

评分只采 3 轮，用标准差/均值阈值 10% 判断稳定。三点很难区分偶发抢占、热降频与真实分布。依据：src/score.c:21、src/score.c:37、src/score.c:45。

建议使用至少 5 轮，报告 median、MAD/IQR 与原始轮次；稳定性标签只描述本次样本内波动，不暗示系统处在理想状态。

延迟评分使用 8 字节步长，节点会密集落在同一缓存行

P1 · 算法

评分档案对六项统一设置 stride=8，指针链节点因此每行多个，延迟混入同一 Cache line 命中与局部访问效应。依据：src/score.c:22、src/memory.c:31。

建议仅对 latency 使用独立固定步长，例如 64 字节，并在 profile 中分别记录 streaming/random/latency stride；不要把 64 写死为对未知 Cache line 的硬件假设。

已加入架构快照，但仍缺完整实验环境指纹

部分完成

当前已输出 CPU 型号、内核、机器架构、页大小、字节序、指针宽度、可检测的 L1d/L2/L3、允许 CPU 集与 NUMA 节点。仍缺实际执行 CPU、完整编译参数、THP 状态和经过验证的 NUMA 页落点。依据：src/output.c、src/platform.c。

后续继续增加可缺失的 build/environment 字段；探测失败写 unknown/null，不能使评分失败。自定义 -O3 -march=native 仍必须能从结果中识别。

评分没有进入常规 CTest，地址序列也没有评分级哈希

P1 · 测试

CTest 只跑很小的详细模式，--score 仅测试非法参数；完整评分是手工烟雾测试。评分 JSON 的分项也不展示每项 sequence hash。依据：tests/integration.py:23、tests/integration.py:77、tests/unit.c。

建议增加测试专用短评分 profile，不改变发布 v1；验证六项、有限值、几何平均重算、固定字段、JSON/CSV 和地址哈希。发布评分记录每项 sequence hash。

单几何平均混入不同访问维度，最好拆成两个主指数

P1 · 评分设计

顺序流式、独立随机请求和串行依赖延迟被统一换算为 Mops/s 后等权几何平均。分数能保留，但“内存性能”含义过宽，且会受编译器向量化和 MLP 影响。

建议保留 MMark 作为版本化摘要，同时报告 streaming throughput 与 random/latency responsiveness 两个分组指数；分组计算方法要单测和版本化。

随机 trace 固定且会带来未计费索引流

P1 · 代表性

地址数组只构建一次，各轮重复；它有可复现优点，但会形成额外的 Cache/DRAM 流，且有放回随机写会产生重复热点。依据：src/memory.c:37、src/bench_random.c:5。

建议保留现有模式并命名为 warm fixed trace；另加每轮再生/双缓冲 trace、无放回排列访问，并报告索引字节、唯一地址数和覆盖率。

自动化测试缺少关键测量语义和故障注入

P1 · 测试

当前测试重访问计数与输出结构，缺少线程起跑偏斜、评分成功路径、索引数组二次分配失败、实际 CPU 绑定、评分环境元数据。Python 测试依赖 assert，设置 PYTHONOPTIMIZE 时可能被跳过。

建议把集成断言改为显式失败函数或 unittest；增加 score smoke、allocation fault injection、并行时间语义断言和评分 schema 兼容测试。

写模式数据过于一致，可能受压缩或特殊路径影响

P1 · 数据

顺序写整块写同一个值，随机写也写同一个值。多数平台无内存压缩，但这不是最稳健的基准数据模式。依据：src/bench_seq.c:14、src/bench_random.c:6。

建议使用低开销的地址相关值，例如 value ^ index，同步调整验证；性能语义保持为逻辑 8 字节写。

覆盖模式还缺少最常用的内存工作负载

P1 · 覆盖度

现有六项覆盖基础读写、混合、随机和单链延迟，但没有 Copy/Triad、页步长/TLB sweep、多链 MLP、固定总容量并行分片、同核 SMT 对照。

建议按实际用途排序增加 Copy/Triad、TLB sweep、多链追逐；这三种对解释真实应用最有价值。每项都必须明确流数量、逻辑字节和索引开销。

NUMA 仍是明确的平台能力缺口

P2 · 可选能力

当前仅按 OS first-touch 分配，绑定 CPU 不等于绑定内存节点，也没有验证页落点。依据：src/bench_parallel.c:42。

建议Linux 可选实现 local/bind/interleave 策略，验证实际 node；容器限制或无权限时显式失败，不静默退化。保持为高级模式，不混入基础分。

普通缓存写与 DRAM 写回语义之间仍缺流式写模式

P2 · 可选能力

当前 store 后只有 C11 顺序栅栏，正确，但不会 flush 脏行。工具尚无 non-temporal/streaming store。

建议在 x86/ARM 能力探测明确时加入独立模式，单列写分配与回写语义；不并入现有固定分数。

跨平台与工程发布矩阵不完整

P2 · 工程

Linux x86_64 已充分验证；Windows/MSVC、Windows clang-cl、ARM64 尚无 CI。计时失败路径仍直接 abort()，不适合可诊断 CLI。

建议使用错误码/消息替代计时 abort，并建立 Linux GCC/Clang、Windows、ARM64 构建矩阵。性能数值不在 CI 比较，只跑正确性与 schema。

子代理与本地审查的合并结论

双方一致

  • 基础内核与环验证扎实，不该推倒重做。
  • 当前分数是产品内 warm logical-access 摘要，不应包装成跨机器 DRAM 排名。
  • 最高收益是修语义、补评分自动化、补环境元数据。
  • 不能通过关缓存、切 governor 或要求 root 来“提升”成绩。

各自补充

  • 子代理首先发现评分 192/256 MiB 自相矛盾，以及并行完成吞吐语义。
  • 本地审查补充了评分 latency stride=8、评分序列哈希缺失、固定值和 Python assert 风险。
  • 最终顺序统一为：正确性 → 评分自动化/元数据 → 统计与并行语义 → 新工作负载 → NUMA/平台。

暂不建议做

不默认关闭缓存、清空 LLC、修改 governor 或要求管理员权限。

不把 cached-store 后的 memory fence 宣称为 DRAM writeback。

不为跨机器排行榜仓促设置绝对参考基线；先稳定 profile 与环境元数据。

不把未实机验证的 Windows/MSVC、ARM 或 NUMA 表述为已经兼容。

建议下一批改动

  1. 修正评分边界：192 MiB → 256 MiB，补 255/256 MiB 边界测试。
  2. 修评分物理含义：latency 单独使用 64 字节步长；把 profile 标为 warm、residency unknown。
  3. 补环境指纹：CPU 型号、内核、LLC、实际执行 CPU、完整编译 flags、THP/NUMA 可检测项。
  4. 补 score smoke：测试专用短 profile，验证六项、formula、JSON/CSV、sequence hash 和固定字段。
  5. 再改并行计时：记录每线程 start/end，输出起跑偏斜与重叠率，明确 completion throughput。
  6. 提升统计：至少 5 个评分轮次，加入 MAD/IQR 与分组指数。
  7. 扩模式：Copy/Triad → TLB sweep → 多链 chasing → 固定总工作集并行分片。
